# PyPI release path

The first `novirhiza-tether` publication is held until every required P0 gate in [TP-001](helix/03-test/test-plan.md) passes. The [deployment checklist](helix/05-deploy/deployment-checklist.md) records the exact local Python 3.11 build, installed-profile checks, immutable GitHub release identity, fresh asset verification, and PyPI upload order. Do not create a stable tag or upload a package while a required gate remains open.

Release staging and PyPI upload no longer run in GitHub Actions. The release operator runs the complete `make check` gate, builds one wheel and source distribution from the annotated stable tag, creates `release-manifest.json` with `scripts/verify_release_artifacts.py`, and attaches those three files to a draft GitHub release. After publishing the immutable release, the operator downloads its assets into a fresh directory and runs the same verifier against GitHub's reported asset digests. Only those verified distribution files may be uploaded to PyPI. Pull requests retain one small Python 3.11 `make pr-check` Actions gate; branch pushes no longer duplicate it. The PR gate does not qualify a release: complete test, coverage, integration and installed-profile checks remain mandatory at the explicit release gate.

The former trusted-publisher workflow used GitHub Actions OIDC, which cannot supply a token to a local upload. No pending publisher for `novirhiza-tether` has been verified; even one would not reserve the name or authenticate the local path. Because the project has not yet been created on PyPI, the first direct upload requires an **account-scoped PyPI API token** supplied securely as `UV_PUBLISH_TOKEN`. Do not paste the token into chat, a command argument, source control, or release assets. After the project exists, replace it with a project-scoped token for any later direct upload. See [PyPI's API-token guidance](https://docs.pypi.org/publishing/publishing-to-pypi/) and [uv's publish guide](https://docs.astral.sh/uv/guides/publish/).

PyPI will not replace an existing filename. If a published release is broken, yank it and publish a corrected new version; keep the original tag, release assets, and manifest unchanged.
